# แผนพัฒนาระบบ: เทียบฟังก์ชันที่ควรมีกับสถานะจริงของโค้ด (2026-08-20)

> จัดทำจากการตรวจโค้ดจริงใน `server/`, `client/src/`, `shared/` และ `docs/` เทียบกับตารางฟังก์ชันที่เสนอมา ไม่ได้อ้างอิงจากความจำหรือสมมติฐาน — ทุกแถวมีไฟล์อ้างอิงที่ตรวจสอบได้

## ตารางสถานะ

| ลำดับ | ฟังก์ชัน | สถานะ | หลักฐานจากโค้ด | ส่วนที่ยังขาด |
|---|---|---|---|---|
| P0 | สิทธิ์ผู้ใช้ตามบทบาท + Audit Log | **มีแล้วเป็นส่วนใหญ่** | 3 บทบาท (`SYSTEM_ADMIN`/`DOCTOR`/`ASSISTANT`) บังคับที่ server ผ่าน tRPC middleware (`server/_core/trpc.ts`); `auditEvents` บันทึกผู้กระทำ เวลา action และ outcome ในทุก mutation สำคัญ (ลงทะเบียน, triage, วินิจฉัย, สั่งยา, จ่ายยา, invoice, payment, จัดการบัญชี, เลขบัตร) | (1) Audit เก็บ action + metadata แบบปลอดภัยเท่านั้น ไม่เก็บค่า "ก่อน/หลัง" แบบเต็ม (ตั้งใจ เพื่อไม่ให้ข้อมูลคลินิกหลุดเข้า log) — เป็นทางเลือกเชิงนโยบายที่ต้องยืนยันกับเจ้าของระบบ ไม่ใช่บั๊ก (2) ยังไม่มีหน้าจอดู audit log ให้ SYSTEM_ADMIN (3) ระบบไม่มีบทบาท "เจ้าของ" เดี่ยว ๆ — สิทธิ์เจ้าของถูกแยกเป็น DOCTOR (คลินิก) กับ SYSTEM_ADMIN (บัญชี/ราคายา/รายงาน, zero-PHI) ถ้าหมอพัลลภต้องทำทั้งสองอย่างต้องมี 2 บัญชี |
| P0 | การคุ้มครองข้อมูลผู้ป่วย (PDPA) | **มีบางส่วน** | Data minimization ตามบทบาท, session timeout 8 ชม. + auto sign-out, login rate limiting, CSV export กันสูตรคำนวณและไม่ส่งออก PHI, เลขบัตรประชาชนเข้ารหัส+mask | (1) ยังไม่มี privacy notice/consent ให้ผู้รับบริการเซ็นตอนลงทะเบียน (2) private document storage (เก็บใบยินยอม/สำเนาบัตร) ยังไม่เปิดใช้ — มีแค่ type `DocumentKind` แต่ไม่มี table/router จริง (3) backup/recovery มีแนวทางเป็นเอกสาร (`docs/operations-readiness-runbook.md`) แต่ยังไม่มีหลักฐานทดสอบ recovery จริง |
| P1 | ทะเบียนคนไข้และค้นหาแบบรวดเร็ว | **มีบางส่วน** | ค้นหาด้วย HN/ชื่อ/นามสกุลใช้งานได้จริง (`frontDesk.searchPatients`, `findPatientByHn`) | (1) ไม่มีการแจ้งเตือนกรณีข้อมูลอาจซ้ำตอนลงทะเบียนใหม่ (เช่น ชื่อ+วันเกิดตรงกับคนที่มีอยู่) (2) ไม่มีหน้าประวัติการรับบริการแบบสรุปของผู้ป่วยรายคน — Doctor Console เห็นเฉพาะ encounter ปัจจุบัน ไม่เห็นประวัติ visit ก่อนหน้า |
| P1 | นัดหมายและคิวรายวัน | **ยังไม่มี** | ระบบปัจจุบันเป็นคิว walk-in ในวันเดียวกันเท่านั้น (`queueEntries`, `QueueBoard.tsx`) ไม่มีการนัดล่วงหน้า | ต้องสร้างใหม่ทั้งหมด: ตารางนัดหมาย, มุมมองวัน/สัปดาห์, สถานะไม่มาตามนัด — เป็นฟีเจอร์ใหญ่ ควรแยกเป็นเฟสของตัวเอง |
| P1 | เตือนนัดและติดตามผล | **ยังไม่มี** | ขึ้นกับระบบนัดหมายซึ่งยังไม่มี | นอกจากรอฟีเจอร์นัดหมาย ยังต้อง**ตัดสินใจช่องทางแจ้งเตือน** (SMS / LINE OA / โทรตามรายชื่อด้วยมือ) ซึ่งทุกทางเลือกที่เป็นบริการภายนอกขัดกับกฎ "ใช้เทคโนโลยีน้อยที่สุด" ที่ยึดไว้ — ต้องคุยกับเจ้าของระบบก่อนเริ่ม |
| P1 | บันทึกการตรวจแบบ Template | **ยังไม่มี** | Doctor Console ใช้ฟอร์ม SOAP อิสระ (S/O/A/P เป็นข้อความอิสระ) ไม่มี template สำเร็จรูปตามประเภทบริการ (`DoctorConsole.tsx`) | ควรทำคู่กับ "ชุดคำสั่งยาด่วน" ที่ backlog ไว้แล้ว ให้แพทย์สร้าง/เลือก template SOAP ตามประเภทเคสที่พบบ่อย |

| P2 | ยาและเวชภัณฑ์แบบง่าย | **มีเป็นส่วนใหญ่** | ตัดสต็อกแบบ FEFO เมื่อจ่ายยา, ติดตาม lot/วันหมดอายุ, นำเข้า CSV, และ Reports ก็นับ lot ที่จะหมดอายุใน 30 วันให้แล้ว (`getAggregateOperationsReport`) | ยังไม่มีจุดสั่งซื้อขั้นต่ำ (reorder point) แยกจากเรื่องวันหมดอายุ — ยังไม่มีการแจ้งเตือน "ของใกล้หมด" ตามจำนวนคงเหลือ |
| P2 | Dashboard เจ้าของคลินิก | **มีเป็นส่วนใหญ่** | `Reports.tsx` + `operationalSummary` ให้จำนวน visit, ยอดรับชำระ, แนวโน้มรายวัน, ยาที่จ่ายสูงสุด, จำนวน lot ใกล้หมดอายุ — ทั้งหมด zero-PHI และทุกบทบาทเปิดดูได้ | ยังไม่มี: ยอดขายแยกตามวิธีชำระ, จำนวน/ยอดใบแจ้งหนี้ที่ยังไม่รับชำระ, จำนวนไม่มาตามนัด (ต้องรอระบบนัดหมาย) |
| P3 | รายงานส่งออกที่ปลอดภัย | **มีแล้ว** | Export CSV ป้องกัน formula injection, จำกัดเฉพาะข้อมูล aggregate ไม่มี PHI, จำกัดสิทธิ์ตาม role | การ export CSV เองยังไม่สร้าง audit event แยก (ปัจจุบัน export ทำจากข้อมูล aggregate ที่ query ไปแล้วฝั่ง client) — ความเสี่ยงต่ำเพราะไม่มี PHI แต่ถ้าต้องการ audit ทุกการ export ต้องเพิ่ม |
| P3 | การจัดการเอกสารประกอบ | **ยังไม่มี** | มีแค่ type `DocumentKind` ใน `shared/clinic-domain.ts` ไม่มี table/router/UI จริง — ตรงกับที่ระบุไว้แล้วใน `docs/project-status-report-th.md` และ `todo.md` | รอ workflow เอกสาร, สิทธิ์เข้าถึง, retention และพื้นที่จัดเก็บที่อนุมัติก่อน (ของเดิมค้างมาตั้งแต่ session ก่อน) |

## แผนพัฒนาแบ่งเฟส (เรียงตามความเสี่ยง/ความคุ้มค่าต่อคลินิกขนาดเล็ก)

**เฟส A — ปิดช่องว่างความปลอดภัย/ตรวจสอบย้อนหลัง (ต่อยอดของที่มีอยู่แล้ว ไม่ต้องออกแบบใหม่มาก)**
1. หน้าจอ Audit Log สำหรับ SYSTEM_ADMIN (มีใน backlog แล้ว)
2. Privacy notice / consent checkbox ตอนลงทะเบียนที่ Front Desk
3. แจ้งเตือนกรณีข้อมูลผู้ป่วยอาจซ้ำก่อนสร้าง HN ใหม่
4. หน้าประวัติการรับบริการแบบสรุปของผู้ป่วยรายคน
5. เพิ่ม audit event ตอน export รายงาน CSV

**เฟส B — ทำให้งานหน้าร้าน/การเงินสมบูรณ์ขึ้น**
6. ส่วนลดที่ต้องระบุผู้อนุมัติ (SYSTEM_ADMIN หรือ DOCTOR) พร้อม audit
7. หน้าจอตรวจนับ/ปิดยอดเงินสดประจำวัน
8. Template บันทึกการตรวจ (SOAP) ตามประเภทบริการ — ทำคู่กับชุดคำสั่งยาด่วนที่มีอยู่แล้วใน backlog
9. จุดสั่งซื้อขั้นต่ำ (reorder point) และแจ้งเตือนของใกล้หมดตามจำนวน
10. เพิ่ม Dashboard: ยอดขายแยกตามวิธีชำระ, ยอดใบแจ้งหนี้ค้างชำระ

**เฟส C — ฟีเจอร์ใหญ่ที่ต้องตัดสินใจเชิงธุรกิจก่อนเริ่ม**
11. ระบบนัดหมายล่วงหน้า (ปฏิทินวัน/สัปดาห์, สถานะไม่มาตามนัด) — งานใหญ่ ควรแยกออกแบบ schema ใหม่
12. ระบบเตือนนัด/ติดตามผล — **ต้องเลือกช่องทางแจ้งเตือนกับเจ้าของระบบก่อน** เพราะทุกทางเลือก (SMS/LINE OA) เป็นบริการภายนอกที่ต้องอนุมัติงบและสิทธิ์การเข้าถึงข้อมูลติดต่อ
13. Private document storage + consent capture ผ่านกล้อง (ค้างจาก session ก่อน รอ workflow ที่อนุมัติ)

## หมายเหตุสำคัญ

- รายการ ICD-10 lookup, ชุดคำสั่งยาด่วน, พิมพ์ฉลาก/ใบเสร็จ/ใบรับรอง, QR PromptPay ที่ระบุไว้จากพิมพ์เขียวเดิมยังอยู่ใน `todo.md` เหมือนเดิม ไม่ได้ซ้ำในเอกสารนี้
- payment method ปัจจุบันมี "เงินสด" และ "เลขอ้างอิงภายนอก" (กรอกเลขอ้างอิงเอง) ซึ่งใช้แทนการรับ PromptPay แบบ manual ได้อยู่แล้ว ส่วนการสร้าง QR code จริงยังเป็นงานแยกต่างหาก
- เอกสารนี้เป็นการวิเคราะห์เท่านั้น ยังไม่ได้เริ่มเขียนโค้ดของเฟส B/C — รอการยืนยันลำดับความสำคัญจากเจ้าของระบบก่อนเริ่มแต่ละเฟส
